## 今天学到了什么

### 环境部分

- Windows 虚拟环境和 WSL/Linux 虚拟环境不能直接混用。
- 虚拟环境不适合通过改名或移动目录来复用，因为其配置可能记录原解释器路径。
- 为每个项目创建独立的 `.venv`，可以避免旧项目的依赖版本影响新项目。
- 不能只根据“安装过程没有报错”判断环境正常，应实际导入库并执行一次最小运算。

### 图像处理部分

- 彩色图像的 `shape` 通常为 `(高度, 宽度, 通道数)`；灰度图通常为 `(高度, 宽度)`。
- `uint8` 表示每个数使用 8 位无符号整数保存，取值范围为 0～255。
- OpenCV 默认使用 BGR 通道顺序，因此 `[255, 0, 0]` 表示蓝色，而 `[0, 0, 255]` 表示红色。
- 像素索引 `image[row, column]` 先写行、再写列，也就是先 `y`、再 `x`。
- `cv2.resize()` 的尺寸参数使用 `(宽度, 高度)`，与 NumPy 的 `shape` 顺序不同。
- 灰度图的每个像素只有一个亮度值；它仍可包含 0～255 的多个灰度等级，并不等于二值图。

## 最小实验与观察结果

### 实验 1：手工创建 3×4 彩色图像

- 修改的像素：`[0,0]`、`[1,1]`、`[2,2]` 和 `[0,3]`。
- 运行前的预测：能正确预测蓝、绿、红三种颜色，但最初把未赋值的 `[1,2]` 误认为 `[0,255,255]`。
- 实际输出：`shape == (3,4,3)`，未赋值像素保持 `[0,0,0]`。
- 预测与结果是否一致：大部分一致；通过输出纠正了像素坐标与颜色值混淆的问题。

### 实验 2：BGR 与 RGB 显示顺序

- 将 BGR 数组直接交给 Matplotlib 后，蓝色和红色互换，黄色变为青色，绿色不变。
- 使用 `cv2.cvtColor(image, cv2.COLOR_BGR2RGB)` 交换红、蓝通道后，Matplotlib 显示正确。

### 实验 3：真实文档照片灰度化

- 输入彩色图尺寸为 `(2275, 1279, 3)`，灰度图尺寸为 `(2275, 1279)`。
- 手工加权公式与 OpenCV 结果的平均绝对差异约为 `0.513`，最大差异为 `1`。
- 在手工结果转为 `uint8` 前加入 `np.rint()` 后，平均差异和最大差异均变为 `0`，全部 `2,909,725` 个像素与 OpenCV 完全一致。
- 灰度化保留空间结构、明暗、文字和边缘，丢失色相与饱和度信息。

### 实验 4：加权灰度与简单平均灰度对比

- 白色纸张和浅色背景在两种方法下差别较小，底部彩色花纹区域差别最明显。
- 纯白像素 `[255,255,255]` 在加权法和平均法中都得到 255；对于接近灰色的像素，三个通道值相近，因此两种方法通常也较接近。
- 彩色像素的三个通道值差异较大，加权法与等权平均法对不同通道的贡献判断不同，因此结果差异更明显。
- 加权法更符合人眼对亮度的感知，尤其体现了人眼对绿色更敏感、对蓝色相对不敏感。
- 当前照片中纸张和桌面都偏亮，部分纸张边界的灰度对比不强，这是后续边缘检测的潜在难点。
- 当前图片中，平均法与加权法的平均绝对差异约为 `2.337`，最大差异为 `14`；整体差异较小，但局部彩色区域可能有明显差异。

### 实验 5：HSV 三通道观察

- OpenCV HSV 输出范围为：`H: 0～179`、`S: 0～255`、`V: 1～255`。
- 白纸和浅色桌面在 S 通道中整体较暗，说明低饱和度；底部彩色花纹更容易在 S 通道中与白纸拉开差异。
- 阴影在 V 通道中偏暗，V 主要反映亮度。
- 白色、灰色等低饱和度区域即使存在 H 数值，其色相也不可靠；应结合 S 判断 H 是否有意义。

### 实验 6：更换图片复验灰度与 HSV 结论

- 新图尺寸为 `(1530,1080,3)`，共有 `1,652,400` 个像素。
- 手工加权灰度与 OpenCV 灰度仅有 5 个像素相差 1，其余 `1,652,395` 个像素完全相同；平均差异约为 `3.03×10⁻⁶`，最大差异为 1。
- 少数差异来自像素值恰好处于浮点公式与 OpenCV 内部整数实现的取整边界，不表示公式或通道顺序错误。
- 平均法与加权法的平均绝对差异约为 `6.184`，最大差异为 `22`，明显高于第一张图片的约 `2.337` 和 `14`。
- 新图包含更大面积的绿色、粉色、黑色与彩色纹理，B、G、R 通道差异更明显，因此不同灰度权重产生了更明显的结果差异。
- 实验说明：同一算法在不同图片上的数值表现会变化，应使用多张图片验证结论，不能只根据单个样本判断方法完全一致或效果稳定。

### 实验 7：等比例缩放与坐标回映

- 原图尺寸为 `(1279,1706,3)`，固定目标宽度 600 后，缩放比例约为 `0.35170`，小图尺寸为 `(450,600,3)`。
- 小图坐标 `(150,200)` 映射回原图得到 `(426,568)`；两张标记图中的红点保持相同的相对位置，验证回映正确。
- 理论上等比例缩放使用同一个比例，但目标高度需要取整：`1279×0.35170≈449.824` 被取为 450，因此实际 `x`、`y` 回映比例存在极小差异。
- 为减少尺寸取整造成的坐标误差，回映时分别根据实际图像尺寸计算 `width/small_width` 和 `height/small_height`，比直接使用 `1/resize_ratio` 更稳妥。
- 文档检测可以在小图上执行以降低计算量，最终透视变换应在原图上执行以保留文字与纹理细节。

### 实验 8：灰度直方图与稳健动态范围

- 全局直方图整体偏向中高亮度，并出现多个明显峰：约 10～25 的深色区域、约 135～150 的纸袋主体、约 185～210 的白色桌面和纸张区域。
- 最小值和最大值只要各有一个极端像素就可能变成 0 和 255，无法说明大部分像素是否覆盖完整动态范围。
- `p1～p99` 忽略两端各 1% 的极端像素，比 `min～max` 更稳健地描述主体像素的亮度跨度；极端像素不一定都来自曝光错误，也可能是图中真实的黑色物体、反光或文字。
- 高对比度图像的灰度分布通常更宽，低对比度图像通常集中在较窄区间；是否出现多个峰还取决于场景包含多少类不同亮度区域。
- 全局直方图只统计亮度数量，不保存像素位置或物体身份；把某个峰归因于纸袋或桌面需要结合原图，若需定量确认应分别统计 ROI 或掩膜区域。

## 今天踩了什么坑


### 1. 旧环境不能在 Windows 中直接使用

- 现象：环境中存在 `bin/python`，但没有 Windows 常见的 `Scripts/python.exe`。
- 定位：查看 `pyvenv.cfg`，发现解释器路径为 `/usr/bin/python3.12`。
- 原因：这是在 WSL/Linux 中创建的环境，不是 Windows 虚拟环境。
- 解决：保留旧环境，为当前项目创建新的 Windows `.venv`。

### 2. `py` 启动器没有识别新安装的 Python

- 现象：安装后运行 `py -3.11` 仍提示没有 Python。
- 定位：查看安装日志，确认 Python 本体和 pip 均安装成功；随后直接使用安装目录中的解释器验证。
- 原因：旧启动器没有正确识别新解释器，但 Python 本体并未安装失败。
- 解决：用 Python 本体创建项目 `.venv`，VS Code 直接绑定 `.venv`。
- 教训：根据日志区分“解释器安装失败”和“启动器发现失败”，不要盲目重装。

### 3. BGR 颜色注释写反

- 现象：最初把 `[255,0,0]` 注释为红色，把 `[0,0,255]` 注释为蓝色。
- 原因：沿用了常见的 RGB 顺序，但 OpenCV 默认使用 BGR。
- 解决：根据 `[B,G,R]` 重新检查并修正注释。
- 教训：颜色显示异常时，先检查通道顺序，不要立即怀疑图片损坏。

### 4. 把未赋值像素与新增颜色值混淆

- 现象：预测 `image[1,2]` 为 `[0,255,255]`，实际结果为 `[0,0,0]`。
- 原因：`[1,2]` 从未赋值，`np.zeros()` 创建后仍保持全零；`[0,255,255]` 是后来准备写入另一个坐标的颜色值。
- 解决：分别追踪“像素坐标”和“写入该坐标的通道值”。

### 5. 混淆数组维度与颜色通道

- 现象：看到灰度图 `shape == (2275,1279)`，误以为它有两个通道。
- 原因：把二维数组的两个空间维度误当成颜色通道。
- 解决：明确 `(2275,1279)` 分别表示高度和宽度；每个位置只有一个标量，因此灰度图是单通道。
- 教训：数组有几个维度，不等于图像就有几个颜色通道。

### 6. 把灰度图理解为只有黑白两色

- 现象：认为灰度图因为“黑白”而默认有两个通道或两种值。
- 原因：混淆了灰度图与二值图。
- 解决：灰度图通常包含 0～255 的连续亮度等级；二值图才通常只有 0 和 255。

### 7. 手工灰度化与 OpenCV 相差 1

- 现象：平均绝对差异约为 `0.513`，最大差异为 `1`。
- 定位：检查手工公式正确，随后注意到 `.astype(np.uint8)` 会直接截断小数。
- 原因：手工浮点计算的截断方式与 OpenCV 内部的取整及优化整数计算略有不同。
- 解决：在转换为 `uint8` 前使用 `np.rint()`，再观察差异分布。
- 验证：修正后差异分布为 `{0: 2909725}`，说明此前差异全部来自直接截断小数。
- 教训：数值结果差异很小时，应先检查数据类型和舍入方式，而不是认定算法错误。


## 理解难点与易混概念

### 1. `axis=2` 到底沿哪个方向计算

- 对于彩色图像，`image.shape` 通常是 `(高度, 宽度, 通道)`。
- NumPy 的轴从 0 开始编号：`axis=0` 是高度方向，`axis=1` 是宽度方向，`axis=2` 是颜色通道方向。
- `np.mean(image, axis=2)` 会在每一个固定的像素位置上，把 B、G、R 三个通道值求平均，因此输出不再有通道维度，`shape` 从 `(H,W,3)` 变为 `(H,W)`。
- 记忆方法：先写出 `shape` 中每个位置的含义，再选择要消掉的那个位置作为 `axis`。

### 2. NumPy 与 OpenCV 的宽高顺序不同

- NumPy 图像的 `shape` 是 `(高度, 宽度, 通道)`，对应 `(行, 列, 通道)`。
- `cv2.resize()` 的尺寸参数是 `(宽度, 高度)`。
- 原因是数组索引习惯使用 `[row,column]`，而图像几何尺寸与坐标习惯使用 `(x,y)`，也就是 `(width,height)`。

### 3. “二维数组”与“两个通道”不是同一件事

- 灰度图 `shape == (H,W)` 中的两个数字是空间维度，不是两个颜色通道。
- 每个 `(row,column)` 位置只存一个亮度值，所以它是单通道图像。
- 彩色图 `shape == (H,W,3)` 才显式保存三个颜色通道。

### 4. 灰度图与二值图的区别

- 灰度图通常包含 0～255 的多个亮度等级。
- 二值图通常只有 0 和 255 两种值。
- 灰度化负责去掉颜色信息；阈值分割才负责把多个灰度等级压缩为两类。

### 5. 灰度化方法会影响后续边缘检测

- 边缘检测依赖相邻区域的亮度变化，而不是直接识别“这是纸张”或“这是桌面”。
- 如果纸张和背景转成灰度后的值很接近，即使原图颜色不同，边界也可能变弱或消失。
- 不同灰度权重会改变彩色背景与纸张之间的亮度差，从而影响 Canny 是否检测到连续边缘。
- 当前测试照片的纸张和桌面都较亮，应在后续实验中重点观察纸张左侧、上侧等低对比边界。

### 6. HSV 中白色的饱和度并不高

- 最初预测白纸区域的 S 偏高，实际应偏低。
- 饱和度描述颜色的鲜艳程度，而不是像素有多亮；白色虽然亮度高，但没有明显色彩倾向，因此 S 接近 0、V 较高。
- “亮不亮”主要看 V，“颜色浓不浓”主要看 S，两者不能混用。

### 7. HSV 没有“黑色通道”

- HSV 的三个通道固定为 H、S、V，不存在黑色通道。
- 黑色是一种像素状态，通常表现为 V 很低，而不是一个独立通道。
- 对当前图片而言，区分彩色花纹与白纸最有帮助的是 S 通道，因为彩色花纹饱和度较高、白纸饱和度较低。

### 8. 低饱和度时 H 通道不可靠

- H 表示色相，但只有在颜色具有一定饱和度时才有稳定意义。
- 对白色、灰色、黑色等低饱和度像素，微小噪声就可能使 H 发生明显变化。
- 使用 HSV 做颜色筛选时，通常不能只限制 H，还需要给 S 设置最低阈值。

### 9. `height, width = image.shape[:2]` 包含两步操作

- `image.shape` 是尺寸元组，例如 `(1530,1080,3)`。
- `image.shape[:2]` 对尺寸元组切片，取索引 0 和 1，得到 `(1530,1080)`；结束位置 2 不包含在结果中。
- `height, width = (1530,1080)` 使用序列解包，依次令 `height=1530`、`width=1080`。
- 这行代码只读取尺寸，不会裁剪或修改图像；应与 `image[y1:y2,x1:x2]` 这种图像数组切片区分。

### 10. 图像坐标系的 `y` 轴方向与数学坐标系不同

- 图像坐标原点通常位于左上角，`x` 向右增大，`y` 向下增大。
- `(x1,y1)` 到 `(x2,y2)` 在当前实验中对应从左上角到右下角，而不是右上角。
- NumPy 切片写作 `[y1:y2,x1:x2]`，因为数组先按行再按列；OpenCV 几何点写作 `(x,y)`。

### 11. ROI 切片通常是共享原数组内存的视图

- `roi_view = matrix[1:3,1:3]` 不会复制数据；执行 `roi_view[:] = 255` 后，原矩阵中心的 2×2 区域也变为 255。
- `roi_copy = matrix[1:3,1:3].copy()` 创建独立数组，修改它不会改变原矩阵。
- 需要在 ROI 上直接赋值、涂黑、画标记且必须保留原图时，应先使用 `.copy()`。

### 12. 对比实验使用了不同的 ROI 范围

- 现象：视图实验使用 `[1:3,1:3]`，复制实验误写为 `[1:2,1:2]`。
- 影响：前者得到 2×2 区域，后者只有 1×1；不影响 copy 是否共享内存的结论，但使两组实验不完全对照。
- 解决：将复制实验统一改为 `matrix[1:3,1:3].copy()`。
- 教训：做 A/B 对比时只改变待研究变量，本实验中应只改变有无 `.copy()`，切片范围必须保持一致。

### 13. 混淆尺寸缩放与坐标移动

- 最初把“高度也乘相同比例”理解为避免只在 x 轴上移动。
- 缩放改变的是图像尺寸和像素间距，不是把图像沿某个方向平移。
- 宽高使用相同比例的目的是保持宽高比，避免物体被横向拉宽或纵向压扁。

### 14. `INTER_AREA` 适合缩小并不是因为等比例

- 是否等比例由目标宽高决定，与插值方法无关。
- `INTER_AREA` 在缩小时会综合目标像素覆盖的原图区域，近似对多个原像素做面积平均。
- 这种方法通常能减少高频细节折叠造成的锯齿、摩尔纹和噪点，因此适合下采样。

### 15. Python 的 `round()` 对 `.5` 使用取偶数规则

- 当前实验中，`150×(1706/600)=426.5`，但 `round(426.5)` 得到 426。
- Python 对正好位于两个整数中间的值采用 ties-to-even，即选择最近的偶数；例如 `round(427.5)` 会得到 428。
- 坐标回映时这通常只造成最多 1 像素的差异，但调试精确坐标时需要知道它不是固定向上取整。

### 16. 灰度轴方向判断反了

- 最初把白色桌面判断为 11～50，把黑字和阴影判断为 150 以上。
- 灰度值 0 表示黑，255 表示白，因此深色文字和阴影应更靠直方图左侧，白色桌面应更靠右侧。
- 读直方图时先固定方向：左暗、右亮，再结合原图推断各峰来源。

### 17. 全局直方图不能直接识别物体

- 直方图只保留“每种亮度有多少像素”，丢失这些像素的坐标。
- 即使某个峰接近纸袋的典型灰度，也不能仅凭全局直方图证明该峰全部来自纸袋。
- 若要比较纸袋与桌面的亮度，应利用 ROI 或 mask 分别计算直方图。

## 检查理解

1. `shape == (720,1280,3)` 表示高度 720、宽度 1280、3 个颜色通道。（正确）
2. `image[100,200]` 中，100 是行索引，即纵坐标 `y`；200 是列索引，即横坐标 `x`。（最初把横纵坐标写反，已纠正）
3. `np.mean(image, axis=2)` 沿 B、G、R 通道求平均，每个像素的三个通道被归约成一个标量，因此通道维度消失，结果从 `(H,W,3)` 变为 `(H,W)`。（最初表述为“限制到二维”，已澄清为归约通道轴）
4. OpenCV 提供 BGR 数组，而 Matplotlib 按 RGB 解释输入；若不转换，红、蓝通道会被错误解释并交换显示。（核心判断正确）
5. 白纸在 HSV 中通常 S 较低、V 较高，因为白色明亮但不鲜艳。（正确）
6. 如果纸张与背景的灰度亮度接近，边界两侧梯度较小，边缘会变弱、断裂或完全漏检。（最初只表述为边缘模糊，已补充梯度与漏检结果）
7. 灰度图通常保留 0～255 的多个亮度等级；二值图通常只保留两类值，如 0 和 255。（正确）

完成了图像矩阵、BGR/RGB、灰度化、HSV、ROI、等比例缩放和灰度直方图实验。确认 OpenCV 彩色图使用 `(H,W,3)` 的 BGR 数组，灰度图使用 `(H,W)` 的单通道数组；`axis=2` 表示沿通道轴归约。手工灰度公式在正确取整后与 `cv2.cvtColor` 高度一致：第一张图全部像素一致，第二张图仅 5 个像素相差 1；等权平均法在彩色纹理较多的图片上与加权法平均相差约 6.184、最大相差 22。
